# 备份、恢复与升级

ThreadBeacon 的持久数据只有 PostgreSQL、S3/MinIO 对象、Worker 身份和浏览器 Profile。数据库与对象必须作为同一恢复点备份；Worker 身份和浏览器 Profile 属于节点本地机密，不应进入公开备份。

## 原生备份与恢复

Windows 原生运行需要 PowerShell 7、PostgreSQL 客户端和 MinIO Client (`mc`)。备份脚本生成 PostgreSQL custom dump、完整 Bucket 镜像和带 SHA-256 的 `manifest.json`：

```powershell
pnpm backup:native
pwsh -File scripts/restore-native.ps1 `
  -BackupPath backups/threadbeacon-YYYYMMDD-HHMMSS `
  -TargetDatabaseUrl jdbc:postgresql://127.0.0.1:5432/threadbeacon_restore `
  -TargetBucket threadbeacon-reports-restore `
  -ConfirmRestore
```

恢复脚本先校验所有文件，再使用 `pg_restore --clean --if-exists` 覆盖明确指定的目标数据库，并用 `mc mirror --remove` 使目标 Bucket 与备份一致。不要把生产数据库或 Bucket 当作首次演练目标。

2026-08-29 的本机演练已把 22 个任务和 6 个报告对象恢复到隔离数据库/Bucket，核对后删除隔离目标；证据见 `docs/acceptance/backup-restore-2026-08-29.md`。

## 容器与生产环境

- Compose：优先对 PostgreSQL 与 MinIO API 做逻辑备份，不直接复制正在写入的 volume。另行备份 `worker-state` 与 `browser-profile` volume，并按敏感凭据加密保管。
- PostgreSQL HA：生产应使用托管 PostgreSQL 或 Patroni/云厂商等成熟方案；控制 API 自身不承担数据库选主。恢复演练必须包含 PITR/WAL 策略、RPO 与 RTO。
- 对象存储 HA：使用 MinIO distributed mode 或兼容 S3 的托管对象存储，启用版本控制、跨站复制和生命周期策略。
- 控制 API：可以多副本滚动升级；Flyway 迁移只能向前兼容当前版本。先升级数据库，再逐批替换 API，最后替换 Worker。
- Gateway：当前仅支持单副本内存协调。滚动升级会让 Agent 自动重连，但升级窗口内的任务由控制面租约重新排队；不能把 Gateway 扩为多副本。
- Browser/Worker：StatefulSet 每个副本保留独立 Profile。一次只替换一个副本，并在继续前确认节点重新上报能力。

## 升级检查单

1. 冻结发布版本，运行 `pnpm check`，记录镜像 digest 与迁移清单。
2. 创建数据库和对象存储一致性备份，并在隔离目标完成恢复验证。
3. 暂停计划任务；等待短任务结束，长任务允许由租约恢复。
4. 先升级一个 API/Worker canary，验证健康、抢单、报告写入和下载。
5. 分批升级其余副本；Gateway 单独维护并观察 Agent 重连。
6. 恢复计划任务，核对失败队列、审计日志和对象数量。

本仓库当前没有在 Docker/Kubernetes 主机上完成 HA 与滚动升级演练，因此这些能力不得标记为已验收。
