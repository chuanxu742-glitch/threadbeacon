## 1. 好消息：接缝位置是对的，只是实现全烂

追踪 `job-manager.ts` 的实际数据流：

```
L236  const dataSourceService = DataSourceFactory.createDataSource(job.dataSource)
L282  allRawTexts.push(...result.rawTexts)     // ← 只取 rawTexts
L334  allRawTexts.push(...result.rawTexts)
L379  → clustering
```

而聚类层的入口签名是：

```ts
// clustering/ClusteringService.ts L85
async cluster(texts: string[], options?: ClusteringOptions): Promise<ClusteringResult>
```

**整条下游——聚类 → GLM 痛点分析 → 优先级评分 → 存储 → 前端——只依赖一个契约：`string[]`。**

`videos: any[]` 和 `metadata` 只用于展示和存档，不进入分析核心。

这意味着 **`IDataSourceService` 这个接缝的位置是正确的**，可以在它背后整体换掉数据层而不触碰下游。
问题不在接缝位置，在于接缝背后的 8 个实现全部硬绑 TikHub。

## 2. 坏消息：现有接口编码了一个错误假设

```ts
export interface IDataSourceService {
  searchAndFetch(keywords: string, limit: number): Promise<DataSourceResult>;
  searchWithComments?(keywords: string, options?): Promise<DeepCrawlResult>;
}
```

**这个接口假设"任何数据源都能按关键词搜全站"。**

而合规数据源恰恰做不到这件事：

| 获取模式 | 能否关键词搜全站 | 可用来源 |
|---|---|---|
| 官方全站搜索 | ✅ | 仅 YouTube（100 次/天）、X（$0.005/条）、Reddit（商用 $12k/月起）|
| **用户授权自有账号** | ❌ 只能拿自己的内容 | 抖音/快手/B站/TikTok 的 creator API |
| 第三方供应商 | ✅ 但取决于供应商 | 蝉妈妈/新榜/巨量算数 |

所以二开必须把接口从"单一搜索模式"扩展成**多获取模式**，否则合规路径根本无法接入。

## 3. 目标架构：把「平台」和「供应商」拆成两个维度

现有设计把两者混在一个枚举里（`'tikhub'` 与 `'youtube'` 并列，且 `getSourceDisplayName('tikhub')` 返回 `'douyin API'`）。

新设计：

```
Platform      = 抖音 | 小红书 | B站 | 快手 | YouTube | X | Reddit | TikTok | 视频号
Provider      = official-api | user-authorized | licensed-vendor
AcquisitionMode = searchAll | fetchOwned | fetchByVendor

           ┌─────────────────────────────────────────┐
           │  job-manager（不改）                     │
           │    ↓ 只要 string[]                       │
           │  ClusteringService（不改）               │
           └─────────────────────────────────────────┘
                          ▲
              ┌───────────┴────────────┐
              │  IDataProvider（新）    │  ← 唯一接缝
              └───────────┬────────────┘
       ┌──────────────────┼──────────────────┐
  OfficialApiProvider  UserAuthProvider  VendorProvider
   ├ YouTubeDataApi     ├ DouyinCreator    ├ 巨量算数
   ├ RedditPraw         ├ BilibiliCreator  ├ 蝉妈妈/新榜
   └ XApiV2             └ KuaishouCreator  └ …
```

接口草案：

```ts
export type Platform = 'douyin' | 'xiaohongshu' | 'bilibili' | 'kuaishou'
                     | 'youtube' | 'twitter' | 'reddit' | 'tiktok';
export type ProviderKind = 'official-api' | 'user-authorized' | 'licensed-vendor';

export interface ProviderCapability {
  platform: Platform;
  kind: ProviderKind;
  canSearchAll: boolean;        // 能否全站关键词搜索
  canFetchOwned: boolean;       // 能否取授权账号自有内容
  canFetchComments: boolean;
  quota?: { unit: string; perDay?: number; costPerCall?: number };
  legalBasis: string;           // 该来源的授权依据，落审计日志用
}

export interface IDataProvider {
  readonly capability: ProviderCapability;
  searchAll?(keyword: string, limit: number): Promise<TextBundle>;
  fetchOwned?(accountRef: string, limit: number): Promise<TextBundle>;
  checkAvailability(): Promise<boolean>;
}

// 下游只认这个
export interface TextBundle {
  rawTexts: string[];                 // 唯一进入分析核心的字段
  items: SourceItem[];                // 结构化条目，替代原来的 any[]
  provenance: { provider: string; fetchedAt: string; legalBasis: string };
}
```

关键改进：
1. **`provenance` 字段强制每条数据带来源与授权依据**——这就是调研报告第 8 节要求的审计日志，写进类型里让它无法被绕过
2. **`canSearchAll` 显式声明能力**，前端据此禁用不支持的选项，而不是运行时报错
3. **消灭 `any`**，用 `SourceItem` 替代 `videos: any[]`

### 阶段四：按辖区决策补齐平台

依据 `docs/技术选型调研.md` 第 17 节四象限矩阵，实施顺序由**交付主体所在地**决定：

**若主体在境外（新加坡/香港/BVI）**——最可行象限
1. 先补 `XApiV2Provider`（官方付费，$0.005/条读取）
2. 再补 `InstagramProvider` / 其他国际平台的登出公开数据路径
3. 中国平台只做 `fetchOwned`（用户授权自有账号），**不实现全站搜索**
4. 硬约束写进代码：`searchAll` 一律登出执行，HTTP 客户端做 Cookie/Authorization 头白名单硬拦截

**若主体在境内**
1. 国际平台（YouTube/X/Reddit）可做，但同样限定登出公开数据
2. 中国平台（抖音/小红书/B站/快手/视频号）**全站搜索不实现**，
   只做 `fetchOwned` 或 `VendorProvider` 对接境内持牌供应商（巨量算数/蝉妈妈/新榜）

**两种情况下都不做的**
- 任何形式的签名破解（x-s / a_bogus / x5sec）——触 DMCA §1201，与辖区无关
- 登录态全站采集——见调研报告 17.1，这是**唯一换辖区也不会变好**的选择
- 微信视频号——腾讯 2026-01 已展示 4,195 仓库级下架能力，不需要法院

### 阶段五：GDPR 护栏落地（1.5 天，与阶段三并行）

客户全球化后 GDPR 是绑定约束，护栏必须是**代码约束而非文档**。
完整依据见 `docs/GDPR架构边界.md`。

| 护栏 | 实现位置 |
|---|---|
| 全局令牌桶限速（≤1 QPS/域名 + 指数退避）| provider 基类，遇 429/403 熔断 |
| **登出模式硬保证** | HTTP 客户端 header 白名单，物理上无法携带 Cookie/Authorization |
| **遵守 robots.txt / ai.txt，不绕 CAPTCHA 与登录墙** | provider 基类前置检查。EDPB 03/2026：绕过即判死 LIA 平衡测试 |
| **标识符 ingest 即丢弃** | 字段白名单：丢 handle/userID/头像/主页链接/permalink/精确时间戳/坐标/粉丝数 |
| **文本内 PII 用 Presidio 替换为占位符** | **replace 而非 hash**——hash 属假名化，仍是个人数据 |
| **k-匿名下限 `minSamples ≥ 10`** | `ClusteringOptions`，丢弃小簇。上游默认是 3，**必须改** |
| **代表性引文改写而非原文摘录** | 否则可回搜原帖，linkage 测试失败 |
| **只持久化聚类级输出** | `analysis-storage-service.ts` 改造，原始与中间产物销毁 |
| **日志全面脱敏** | 禁止 `console.log` 原始文本，含错误堆栈——最常见泄漏点 |
| 禁止签名脚本 | CI 阻断项：`rg "_0x[0-9a-f]{4,}" -g "*.js"` 命中即 fail |
| license 隔离 | AGPL/非商用组件独立进程，SBOM 标注边界 |
