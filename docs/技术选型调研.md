## 0. 最重要的一条结论

**License 干净 ≠ 行为合法。这是两套独立的风险，必须分开评估。**

| 风险维度 | 管的是什么 | 判定依据 | 典型踩雷 |
|---|---|---|---|
| 著作权风险 | 你能不能用这段**代码** | LICENSE 原文 | 复用 MediaCrawler 代码做商用 |
| 刑事/竞争法风险 | 你能不能做这个**行为** | 刑法 285/286、反法 13 条 | 复现 X-Bogus 签名去抓抖音 |

最典型的例子：`Evil0ctal/Douyin_TikTok_Download_API` 是 Apache-2.0，**著作权上随便用**；
但它的核心资产是自研的 X-Bogus / A_Bogus / msToken 签名算法，
而最高法入库参考案例「丁某案」((2022)苏0213刑初223号)认定：
**破解抖音 X-Gorgon 加密算法的软件属于"专门用于侵入计算机信息系统的程序"**，判有期徒刑 1 年 6 个月缓刑 2 年。

结论：**这个仓库 license 越干净，越容易让人忽略它的行为风险。**

### MediaCrawler —— LICENSE 原文关键句（已抓取核实）

```
NON-COMMERCIAL LEARNING LICENSE 1.1

"The Software is limited to learning and research purposes only, and may not be
 used for large-scale crawling or activities that disrupt platform operations."

"Without the written consent of the copyright owner, the Software may not be used
 for any commercial purposes or to cause improper influence on third parties."

授权性质："non-exclusive, non-transferable right"
```

三重限制：**禁商用 + 禁大规模爬取 + 不可转让**。
`non-transferable` 尤其致命——意味着连"随产品分发给客户"都不允许，SaaS 交付同样有风险。
且作者主推付费闭源版 MediaCrawlerPro，新能力向付费版倾斜，开源版长期会被弱化。

**它仍是最好的工程参考**（7 平台覆盖、登录态管理、Playwright 规避逆向的思路），但**代码一行都不能进商业产品**。

### bilibili-API-collect —— 归档原因（已抓取核实）

README 记载：2026-01-28 收到 B 站委托律所的律师函，指控该仓库
"系统性收集整理 B 站非公开 API 接口、调用逻辑、参数结构、访问控制与鉴权机制，
并通过技术文档和代码示例向不特定公众传播"。作者随即停止维护、删除相关文档与源码，
2026-01-30 仓库归档。

**这是一个平台主动维权的强信号：B 站方向的采集应视为高风险区。**

### Spider_XHS —— license 冲突陷阱

README 挂 MIT 徽章，但 **仓库根本没有 LICENSE 文件**（main/master 均 404，API 返回 `license: null`），
且 README 正文明写"禁止任何商业化行为"。
→ 徽章不构成有效授权要约，实际状态是**全版权保留**。技术上它的纯 JS 逆向（x-s / x-t / x-s-common，无需浏览器）
是最轻量的方案，但法律上不可复用。

| 项目 | Star | 最近推送 | License | 结论 |

### 反转：feapder 的 NOASSERTION 是误报

GitHub API 报 NOASSERTION，容易被误判为自定义 license。实际读原文是**逐字标准 MIT**，
含 `to deal in the Software without restriction ... and/or sell copies`。
分类器失败的原因仅仅是文件第 1 行 `MIT License` 之后插了一行孤立的 `Modifications:`——
**格式噪音，不是附加条款。可放心商用。**

> 教训：`NOASSERTION` 只说明分类器识别失败，必须读原文才能定性。
> MediaCrawler 的 NOASSERTION 是真限制，feapder 的是假警报。

### 为什么不选 Scrapy

先纠正一个过时论据：**Twisted 已不是主要包袱**。Scrapy 2.13（2025-05）已把
`AsyncioSelectorReactor` 设为默认，2.14 补上 `AsyncCrawlerProcess`，当前 2.17。
拿"Scrapy 是 Twisted 的所以不能用 asyncio"来否决它是引用了旧结论。

真正的否决理由在 **HTTP 层**：逆向 API 场景的胜负手是 TLS/JA3 指纹伪装 + 签名生成 + Cookie 池。
Scrapy 的 downloader 仍绑在 Twisted Agent 上，接 curl_cffi 必须自写 `DownloadHandler`，是纯胶水成本。
Crawlee 原生内置 `CurlImpersonateHttpClient` / `ImpitHttpClient` / `HttpxHttpClient`，开箱即用。

其次，只有 3–5 类 JSON 接口时，Scrapy 的 spider middleware + downloader middleware 双层链路 + signals
属于冗余抽象；LinkExtractor、robots 中间件、HTTP cache 这些 HTML 时代的能力一个都用不到。

代价：Crawlee 生态小得多（9.4k vs 63.6k star），中文资料稀少，遇坑要读源码。
Apify 商业维护 + 日更，长期性可接受。Windows 上曾有 `WindowsSelectorEventLoopPolicy` 崩溃（issue #1204），已修复。

> **例外**：若目标平台 ≤3 且只是分页拉 JSON，直接 `asyncio + httpx/curl_cffi` 手写更省事。
> 无论如何**别选 Scrapy**——它的增量价值全在你用不到的部分。

| 项目 | Star | License | 结论 |
|---|---|---|---|
| microsoft/markitdown | 171,494 | MIT | 文件→MD 转换器，**不是采集工具**，不对口 |
| firecrawl/firecrawl | 161,083 | **AGPL-3.0** | **排除**（见下） |
| unclecode/crawl4ai | 76,077 | Apache-2.0 + 强制署名 | LLM fallback 层可用 |
| D4Vinci/Scrapling | 72,577 | BSD-3-Clause | **推荐**，无 LLM 的自适应选择器 |
| docling-project/docling | 64,250 | MIT | 文档解析，不对口 |
| ScrapeGraphAI | 29,031 | MIT | 纯 LLM 驱动，仅适合原型 |
| adbar/trafilatura | 6,403 | Apache-2.0（≥v1.8） | **正文抽取最优解** |

**firecrawl 排除的双重理由**：核心是 AGPL-3.0；且官方 `SELF_HOST.md` 明示自托管**不含 Fire-engine**——
反爬 / IP 封锁对抗是云端专属，自托管版功能阉割。既有传染风险又拿不到关键能力。

**对结构化 API 平台，LLM 抽取是过度设计。** 小红书 / 抖音 / B 站接口返回结构化 JSON，
逆向后确定性解析：零 token、零幻觉、毫秒级、100% 可复现。

LLM 的正确位置是**两个窄口**：
1. 运行时 fallback：字段缺失率超阈值时触发单页 LLM 抽取并告警
2. 离线修复：改版后用 LLM 重新生成 selector，**产物仍是确定性代码**（crawl4ai 的 `generate_schema` 即此模式）

`trafilatura` 有唯一严肃的公开评测（ScrapingHub 基准最优、Bevendorff et al. 2023 ROUGE-LSum 最佳单工具），
适合作为正文层；`Scrapling` 的 `adaptive=True` 是完全无 LLM 的抗改版自愈方案。

## 6. License 准入判定流程（逐步执行，命中即停）

1. 仓库根目录有无 `LICENSE` / `COPYING`？**无 → 排除**（默认全版权保留，公开 ≠ 授权）
2. 是 SPDX 可识别的 OSI 许可吗？否（自定义 / "仅供学习" / 加禁商用条款）→ **排除**
3. **读 LICENSE 原文**——`NOASSERTION` 可能是真限制（MediaCrawler）也可能是格式误报（feapder），不读原文不下结论
4. LICENSE 与 README / 徽章 / 注释冲突？冲突且未书面澄清 → **排除**（按最严格解释推定）
5. GPL / AGPL 系？→ 进隔离清单：独立进程 + 不修改源码 + 不 import 进主程序
6. 含 non-transferable / 禁大规模爬取 / field-of-use 限制？→ 商业交付 **排除**
7. 通过者登记 SBOM，记录 commit hash 与许可全文快照

**"仅供学习交流，请于 24 小时内删除"** 是单方免责声明，对第三方权利人无效，
不能阻却侵权或入罪，仅表明作者主观无营利故意。**视为无授权。**

**AGPL §13 触发条件**（三者同时满足）：修改了 AGPL 程序本体 + 运行修改版 + 用户通过网络与该 AGPL 程序本身交互。
未修改地部署不触发；用户只与你的独立服务交互、该服务通过进程/网络边界调用 AGPL 组件，通常不触发。
**规避边界：独立进程 + 网络/CLI 调用，禁止同进程 import/link。**

## 7. 供应链审计（Windows + uv + pnpm，无 Docker）

采集类项目特有的高危模式：
- 内嵌混淆 JS 签名算法（需 `node` 执行、不可审计）
- 硬编码第三方签名 / token 服务 URL（TikHub、FastAIToken 类）——**你的 cookie 和请求参数会外发给未知第三方**
- pip / npm typosquatting、requirements 无版本锁定

```powershell
# 锁定与漏洞扫描
uv lock
uvx pip-audit -r requirements.txt --strict --desc
winget install Google.osv-scanner
osv-scanner scan source -r . --licenses --format table

# Node 侧
pnpm install --frozen-lockfile
pnpm audit --audit-level moderate
pnpm config set ignore-scripts true          # 阻断安装期任意代码执行
pnpm config set minimumReleaseAge 1440       # 新包冷静期，抗劫持
```

**揪出 JS 里的外联（静态）**

```powershell
rg -n --pcre2 "https?://[^\"'\s]{6,}" -g "*.js" -g "!*.min.js" | rg -v "(w3\.org|schema\.org|localhost)"
rg -n "fetch\(|XMLHttpRequest|child_process|execSync|eval\(|new Function\(" -g "*.js"
rg -n "_0x[0-9a-f]{4,}" -g "*.js" -c        # 混淆特征
rg -n "^.{2000,}$" -g "*.js" --stats        # 超长单行
```

**动态验证（无 Docker）**：Node 22 的 `--permission` 能封住文件/进程，但**不覆盖网络**，网络需靠防火墙：

```powershell
New-NetFirewallRule -DisplayName "block-node-out" -Direction Outbound `
  -Program "D:\develop\NodeJS\node.exe" -Action Block
```

**断网下签名脚本若报错 → 说明它在外联，直接排除。**

## 8. 法律红线的工程 checklist

> 以下是工程约束，不是法律意见；商用前请律师复核。判例细节建议核对裁判文书原文后再据以决策。

| 法条 | 工程触发动作 |
|---|---|
| 刑法 285 条 2 款 | **突破/绕过技术保护措施**后取数——破解签名、伪造鉴权、盗用他人 cookie |
| 刑法 285 条 3 款 | 把破解签名的采集器**对外发布或售卖** |
| 刑法 286 条 | 高并发打崩目标、篡改对方数据 |
| 个人信息保护法 13/17/28 条 | 采集手机号、真实姓名、位置、私信等，无告知同意 |
| 反不正当竞争法 13 条 3 款（2025-10-15 施行） | 新增数据专条：以欺诈、胁迫、**避开或破坏技术管理措施**获取他人合法持有的数据 |

**参考判例**（供风险标定，非法律结论）：
- 丁某案，(2022)苏0213刑初223号，最高法入库参考案例：破解抖音 X-Gorgon 的软件 = "专门用于侵入的程序"，1 年 6 个月缓 2 年
- 马某某案，(2019)苏1091刑初157号：抓取百度网盘分享链接 + 提取码转售，违法所得 7 万，3 年缓 4 年
- 微梦诉抖音，(2017)京0108民初24530号：一审判赔 2000 万 + 合理开支 115.67 万，二审维持

**公开 vs 登录后的真正分界**：不在"数据本身是否公开"，也不简单等于"有没有登录"，
而在**是否突破了技术保护措施**。这一层要分三档，混为一谈会导致架构决策失误：

| 行为 | 定性 | 风险层级 |
|---|---|---|
| 未登录抓公开可见内容 | 不涉访问控制 | 最低（仍受个人信息与反法约束）|
| **用自有账号正常登录后抓取** | 未突破技术措施，但**违反平台 ToS** | 民事违约 / 不正当竞争，一般不入刑 |
| 破解签名、伪造鉴权、盗用他人 cookie 绕过接口校验 | **突破技术保护措施** | 刑法 285 条 2 款核心射程 |
| 上述行为 + 规模化转售数据 | 加重情节 | 285 条 3 款 / 加重量刑 |

即：**"登录"本身不是分水岭，"破解"才是。** 用自有账号走平台正常的登录流程、
按人类可达的速率取自己可见的数据，与逆向签名绕过鉴权，是两个性质完全不同的行为。
但要注意：自动化登录 + 规模化 + 商业化叠加时，会显著增强"违背商业道德"的认定，
微梦诉抖音一案的 2000 万判赔正是纯民事路径。

**robots.txt**：行业惯例，非法律强制。百度诉奇虎案确立双向标准——爬方应遵守，被爬方的限制也须合理非歧视。
遵守 robots 是不构成不正当竞争的重要抗辩，但**不能免除个人信息与刑事责任**。

**工程化规避设计**
- 全局令牌桶限速（建议 ≤1 QPS/域名 + 指数退避），遇 429/403 立即熔断，绝不并发绕限
- 只采公开数据：在 HTTP 客户端做 header 白名单硬拦截，**代码层面禁止携带 Cookie / Authorization**
- 把"调用 JS 签名脚本"列为 CI 阻断项
- 数据最小化：入库前字段白名单；私信与好友关系直接丢弃

> **勘误（2026-08-05）**：本节初稿曾建议"手机号 / UID 一律 HMAC-SHA256 加盐"。**这是错的。**
> Hash 是可逆映射关系，属于**假名化（pseudonymisation）**，而 EDPB Guidelines 01/2025
> 重申**假名化数据始终是个人数据**，不脱离 GDPR 范围。
> 正确做法是**替换为不保留映射的占位符**（`<PERSON>` / `<EMAIL>`）。详见 `docs/GDPR架构边界.md` §7.4。
- 审计日志：记录每次请求的 URL、时间戳、响应码、robots 命中情况，保留 ≥6 个月，作为"未突破技术措施"的证据
- license 隔离：AGPL / 非商用组件跑独立进程，主程序仅通过 HTTP / CLI 调用，SBOM 标注隔离边界

## 9. 两条路线

选型的分叉点不是技术，是**要不要突破访问控制**。

### 路线 A：合规采集（只碰公开数据）

- 不携带 Cookie / Authorization，不破签名，不建账号池
- 技术栈：`Crawlee for Python` (Apache-2.0) + `curl_cffi` (MIT) + `Scrapling` (BSD-3) + `trafilatura` (Apache-2.0)
- 浏览器层按需 `Patchright` (Apache-2.0)；LLM fallback 用 `crawl4ai` (Apache-2.0，注意署名义务)
- **全栈 license 干净，可商用可闭源**；覆盖面受限于各平台未登录可见的内容
- 适配成本：中。Crawlee 中文资料少，但没有法律尾巴

### 路线 B：逆向采集（签名 + 账号池）

- 需要复现 x-s / a_bogus 等签名，维护 Cookie 池
- 现实是：**这条路上几乎没有 license 干净的可复用代码**——MediaCrawler 禁商用且不可转让，
  Spider_XHS 无授权，weibo-crawler 无授权，bilibili-API-collect 已被律师函归档
- 唯一 license 干净的 `Douyin_TikTok_Download_API`（Apache-2.0），其核心能力恰好对应丁某案的入罪事实
- 即"**能合法拿到的代码，做的是有刑事风险的事；没有刑事风险的事，不需要这些代码**"
- 若仅个人学习研究、不商用不外发不转售，风险显著降低，但 license 限制依然使这些代码无法进入任何对外产品

**推荐路线 A**，把覆盖面缺口用"官方开放平台 API + 公开页面"补，而不是用逆向补。

**民事**

- 淘宝诉美景「生意参谋」案：全国首例大数据产品不正当竞争案，**判赔 200 万元**——**直接对应"行业大盘/竞品分析"业务形态**

**刑事**
- 上海普陀区 2025 年案：绕过验证机制爬取 **8 亿余行**数据，直接损失仅 5 万余元，仍以**提供侵入计算机信息系统程序罪 + 非法获取计算机信息系统数据罪**判处三年至六个月（缓刑）

- 成都双流区案：开发并**售卖**爬取新开网店数据的软件，以**非法控制计算机信息系统罪**判六至八个月

**对 SaaS 交付最致命的一条：案例中被判的是写代码和卖工具的人，不只是使用方。**
「提供侵入程序工具」本身即独立罪名，**把工具交给客户在他自己环境跑，不能消解这个风险**。

### 反爬现状
淘宝 `x5sec` cookie 为接口关键鉴权参数，生成逻辑藏在重度混淆 JS；
滑块依赖 `slidedata` 轨迹 + 浏览器指纹三重校验。
2026 年各平台已升级到 IP 指纹 + ISP 溯源 + Canvas/WebGL/AudioContext 等 300+ 维度检测。

### 合规替代
1. **官方付费数据产品**：生意参谋、京东商智/商麒、拼多多数据魔方——行业大盘和竞品趋势官方就卖，价格远低于打官司
2. **官方 API 做自有店铺**：订单/商品/库存/物流，**这部分可以做，也是唯一能安心商用的部分**
3. **淘宝联盟物料搜索**：字段受限但合法
4. **持牌第三方**：魔镜、情报通、蝉妈妈、飞瓜——需在合同中要求出具数据来源合规证明

## 14. 最终判断：你的需求组合当前不存在合规实现路径

**商用对外交付 + 10 平台全站采集 + 登录态**，这三个约束同时成立时无解：

- 9 个平台只有 **YouTube** 有可商用的官方全站 API（且搜索配额受限）
- **X / Reddit** 买得到但很贵（$10k / $12k 每月起），COGS 可能压垮产品定价
- **小红书、B 站、快手、微信视频号、TikTok、电商竞品数据**——**无任何合规商用路径**
- 这些平台上 license 干净的开源方案，做的恰好是判例中的入罪行为；
  不入罪的做法，又不需要这些开源方案

### 三个可行的产品形态重构（按推荐度）

**形态一：多平台数据接入与治理中台（推荐）**
采集能力只做 ① 官方 API ② 客户授权自有账号数据（抖音/快手/B站/TikTok 均支持 creator 授权模式）；
竞品与大盘数据走持牌第三方对接。商业价值保留，法律风险外移。

**形态二：收缩到可付费合规的平台**
只做 YouTube + X + Reddit，全部走官方付费 API。前提是产品定价能覆盖 $22k+/月的 COGS。

**形态三：改做"客户自有数据"分析产品**
不做全网采集，做客户授权后的自有账号数据分析（内容表现、粉丝画像、竞品需客户自己提供）。
这条路 9 个平台的 creator API 全部可用，法律风险最低。

### 明确不推荐

**把采集器做成客户自部署来转移风险**——判例已证明"提供工具"本身是独立罪名，
且商用交付时你仍是工具的开发和销售方。免责声明不消解风险：上述刑事案例的被告都写了免责声明。

**风险在合同层面根本没有转移**：供应商收费、免责、赔偿封顶 100 美元，
法律后果全部由境内交付主体承担。而中国监管与平台维权**只能找到你**。

### 15.5 "明知"要件使法律地位比自建爬虫更差

这是最反直觉、也最重要的一点：

- 供应商 ToS 首页写明 unofficial → **不可能主张不知情**
- 作者的逆向项目 19.1k star 公开可查 → **"应知"成立无争议**
- README 反向宣称"官方 API 避免法律风险" → 对外交付时若沿用此表述，
  **构成对客户的虚假陈述**，可能额外触发合同欺诈责任

叠加反不正当竞争法第 13 条（2025-10-15 施行）"避开或者破坏技术管理措施"条款——
X-Bogus/A_Bogus 签名伪造正是该条的标准形态。

### 15.6 项目自身的历史（源码考古）

`requirements.txt` 注释里保留了迁移记录，列出**已移除的依赖**：

```
# 数据采集依赖（已改用 TikHub API）：
# - curl-cffi (小红书)
# - pyexecjs (小红书)
# - DrissionPage (抖音旧版)
# - beautifulsoup4 / lxml / httpx / playwright ...
```

`pyexecjs` 执行 JS 正是生成小红书 x-s 签名的典型做法；`DrissionPage` 则是本报告第 3 节
确认「自定义许可禁止商用」的那个库。`package.json` 的项目名仍是 `xhs-pain-point-extractor`。

**即：这不是"一开始就选了合规路线"，而是把自己做的逆向换成了别人做的逆向。**

### 15.7 可借鉴与必须替换

**值得借鉴（与采集合规性无关，是真价值）**
- **产品形态**：社媒评论 → 语义聚类 → 痛点识别 → 商机优先级评分，是清晰的数据增值路径
- **分析层技术选型**：embedding + DBSCAN 密度聚类（`density-clustering` + `ml-distance`），
  比无脑丢给 LLM 更省钱可控，与本报告第 4 节"确定性为主、LLM 收窄到两个口"的结论一致
- 24 小时缓存降本、多语言 i18n、任务异步化 + SWR 轮询

> **勘误**：本节初稿曾称 `data-source-interface.ts` + `data-source-factory.ts` 是
> "可插拔数据源抽象，恰好是替换数据层所需要的"。**读实现后确认该判断错误**，
> 详见 15.9。它是**平台**抽象，不是**供应商**抽象，不存在可替换 TikHub 的接缝。

**必须替换**
- 整个 TikHub 数据层 → 按第 14 节形态一，换成官方 API + 用户授权自有账号数据 + 境内持牌第三方
- **删除 README 中"官方 API 接口，避免法律风险"表述**——这是可被追责的虚假陈述，比技术风险更紧迫

### 15.8 供应商替代建议

| 服务 | 授权状况 |
|---|---|
| ScrapeCreators | 自称 unofficial |
| EnsembleData | 定位 "scraping APIs"，无授权声明 |

## 15.9 二开可行性：代码级评估

### 关键发现：不存在可替换 TikHub 的接缝

`data-source-interface.ts`（45 行）+ `data-source-factory.ts`（69 行）看起来像可插拔抽象，
但读实现后结论相反：

```ts
// data-source-interface.ts —— 这是「平台」枚举，不是「供应商」枚举
export type DataSourceType =
  'tikhub' | 'tiktok' | 'bilibili' | 'wechat' | 'youtube' | 'xiaohongshu' | 'twitter' | 'reddit';
```

`'tikhub'` 与平台名并列，而 `getSourceDisplayName('tikhub')` 返回 **`'douyin API'`**——
供应商与平台概念被混在同一个枚举里。

更决定性的是耦合实测，**8 个平台 service 无一例外硬绑 TikHub 具体类**：

| service | import tikhub-client | 被 `TikHubAPIClient` 类型标注处 |
|---|---|---|
| tikhub / tiktok / bilibili / wechat / youtube / xiaohongshu / twitter / reddit | **全部 True** | **各 3 处** |

```ts
// reddit-service.ts —— 注释写着「Reddit API」，实际注入的是 TikHub 客户端
import { TikHubAPIClient, createTikHubClient } from './tikhub-client';
export class RedditService implements IDataSourceService {
  private client: TikHubAPIClient;          // 具体类，非接口
  constructor(client?: TikHubAPIClient) { this.client = client || createTikHubClient(); }
```

`IDataSourceService` 抽象的是"平台怎么搜"，不是"数据从哪来"。
**要换供应商必须重写全部 8 个 service + 1685 行的 client，没有捷径。**

### 代码量分布（二开成本的真实结构）

| 处置 | 模块 | 行数 |
|---|---|---|
| **必须重写** | `tikhub-client.ts` | 1,685 |
| **必须重写** | 8 × `*-service.ts`（tikhub/tiktok/bilibili/wechat/youtube/xiaohongshu/twitter/reddit） | ≈ 2,400 |
| **直接删除** | `semantic_clustering.py`（与 TS 聚类重复实现，迁移残留） | 556 |
| **可原样保留** | `lib/services/clustering/*`（ClusteringService / EmbeddingProvider / DataCleaner） | ≈ 1,400 |
| **可原样保留** | `glm-service.ts` / `analysis-storage-service.ts` / `priority-scoring.ts` | 865 |
| **可原样保留** | 前端 `src/`（AnalysisForm / DetailModal / ResultsTable / i18n 等） | ≈ 3,000 |

**约 4,100 行要重写，占 `lib/` 的六成以上。**

聚类模块**确认完全解耦**（`clustering/` 下无任何 tikhub 引用，外部依赖只有
`density-clustering`、`ml-distance`、`openai`）——这部分是真资产，可以直接拿走。

### 其他二开风险

1. **README 说支持 8 平台，实际只启用 6 个。** `getEnabledSources()` 返回
   `['tikhub','tiktok','bilibili','wechat','youtube','xiaohongshu']`，
   源码注释："twitter / reddit 工厂类已存在但暂未在后端启用"。
   **讽刺的是，Reddit 和 X 恰好是本报告中唯二 license 与合规双清白的平台，而它们没实现。**
2. **接口层类型安全缺失**：`DataSourceResult` 里 `videos: any[]`、`metadata?: any`，
   `DeepCrawlResult` 里 `allComments: any[]`——换实现时编译器提供不了任何保护。
3. **无测试运行器**：`package.json` 没有 `test` script，也没有 jest/vitest。
   `ClusteringService.test.ts`（435 行）、`run-tests.ts`、`test-simple.ts` 都是手跑脚本，无法进 CI。
4. **任务管理是纯内存**：`job-manager.ts`（669 行）用 in-memory async processing + SWR 轮询，
   serverless 或多实例部署会丢任务，商用必须换持久化队列。
5. **无社区支撑**：120★、0 open issue、2026-02 创建、2026-07-06 后停更。
   重度 AI 生成痕迹（`CLAUDE.md`、0 字节的 `QWEN.md`、39KB 的 `CLUSTERING_MIGRATION_REPORT.md`）。
   上游不会帮你修任何 bug。

### 结论

| 你的产品定位 | 建议 |
|---|---|
| **就是"痛点挖掘 / 商机发现"** | 可以 fork，但要按上表预算重写 `lib/` 六成代码，第一个 commit 就该把 TikHub 层摘干净 |
| **是"多平台采集 / 数据中台"** | **不要 fork**。只取 `clustering/` 与前端组件，数据层从零按供应商抽象重新设计 |

MIT 允许直接复制文件（保留版权声明即可），**不 fork 也能合法拿走想要的部分**。
考虑到要扔的部分占大头、且 TikHub 命名渗透在枚举与显示名里，复制干净模块通常比 fork 后做减法更省事。

# 第四轮：辖区对比 —— 对前述结论的修正

## 16. 前述分析的隐含假设与修正

**本报告第 1–15 节全部建立在一个未经确认的假设上：交付主体在中国境内。**
该假设源于语言与平台组合，从未与需求方核实。以下是解除该假设后的修正。

### 16.1 修正幅度：原结论约 40% 是中国特有的

| 约束 | 性质 | 换辖区后 |
|---|---|---|
| 刑法 285 条 2/3 款 | **中国特有** | 美欧新港无对应低门槛刑事条款，**消失** |
| 反不正当竞争法 13 条数据专条 | **中国特有** | 美国被版权法 preempt，欧盟限缩在 sui generis 范围内，**大幅减弱** |
| 中国刑事程序风险（羁押、扣押设备）| **中国特有** | 境外主体不承担 |
| **开源 license 条款** | **全球通用** | 伯尔尼公约 182 缔约方，**零效果** |
| **平台 ToS 违约** | **全球通用** | 强度不同但都成立 |
| **个人信息法（GDPR / 个保法）** | **全球通用** | 双重域外效力，**躲不掉** |
| **DMCA §1201 反规避** | **全球通用** | 与 CFAA 松绑无关，独立通道 |
| **平台非司法下架能力** | **全球通用** | 不需要任何法院 |

**约 40% 可通过境外主体消解，60% 躲不掉。**

### 16.2 美国：CFAA 已让路，战场转到合同与侵权

- **hiQ v. LinkedIn**（9th Cir. 2022-04-18）：无登录门槛的公开数据"计算机根本没有设门可开关"，不构成 CFAA。
  **但 hiQ 最终输了**——2022-12 和解，承认 50 万美元判决 + 侵占动产责任 + 永久禁止抓取。
- **Van Buren v. United States**（2021）：`exceeds authorized access` 收窄为"访问对你完全禁区的信息"。
- **Meta v. Bright Data**（N.D. Cal. 2024-01）：**登出状态**抓公开数据不违反 ToS；Meta 2024-03 撤诉。
- **X Corp v. Bright Data**（N.D. Cal. 2024-05）：版权法 **preempt** 州法合同/侵权请求，X 全部诉请被驳。
- **反向信号 —— Ryanair v. Booking.com**：涉及**登录后**抓取，2024-07 陪审团认定违反 CFAA，
  2025-01 法官以损失未达 $5,000 门槛推翻，2025-02 上诉第三巡回**尚未终审**。

> **美国现状：登出抓公开数据风险很低；一旦登录、注册账号或绕过技术措施，风险立刻回来。**
> 这一条直接否定了"用自有账号登录后采集"在美国辖区的安全性。

**CCPA/CPRA 的关键分歧点**：§1798.140 把"publicly available"排除在 personal information 之外，
含"消费者自行向公众公开的信息"。社媒公开帖文大概率落入豁免——**这是美国与 GDPR/个保法的根本差异**。

### 16.3 欧盟：最严，且"公开"不豁免

- **GDPR 无"公开数据"豁免**。EDPB Opinion 28/2024 确认正当利益可作合法性基础，但须过三步 LIA 测试。
- **Art. 14 告知义务是实操死结**：波兰 DPA 罚 Bisnode 22 万欧元（750 万条抓取记录），
  明确认定"成本过高"（估算约 4000 万欧元邮寄费）**不构成** Art.14(5)(b) 的"不成比例努力"。
- **Clearview AI**：法国/意大利/希腊各 2000 万欧元、荷兰 3050 万欧元，合计约 1 亿欧元。
  **Clearview 是美国公司、无欧盟实体，仍被认定受 GDPR 管辖**——这是"境外主体不能规避"的最强判例。
  英国 ICO 750 万英镑罚单经 2025-10-06 Upper Tribunal 推翻原裁定，确认 ICO 有管辖权。
  **但罚款至今未支付**，反映执行力受限。
- **数据库权反而不利**：*Ryanair v. PR Aviation*（CJEU C-30/14, 2015）——数据库若不受版权/sui generis 保护，
  用户例外也不适用，**网站可用合同条款自由禁止抓取**。
- **DSA Art. 40(12)** 只对经审核研究人员开放，商业产品不适用。
- **AI Act Art. 53(1)(c)**：若产品用于训练或供训练，须尊重 DSM 指令 Art.4(3) 的机器可读 TDM opt-out。

### 16.4 新加坡 / 香港：对抓取本身规制最松

| | 新加坡 | 香港 |
|---|---|---|
| 未授权访问 | CMA s.3，主要针对"正常不可达"部分（隐藏链接、后门）| 《刑事罪行条例》s.161 经 **SJ v Cheng Ka Yee [2019] HKCFA 9** 大幅收窄，不适用于使用自己的设备 |
| 个人数据 | PDPA 对**公开可得**个人数据免同意；2021 起新增正当利益例外 | PDPO 无明确公开豁免，执法强度低 |
| 执法 | PDPC 罚单主要针对泄露/安全事件，非抓取行为本身 | 低 |

> 未验证：未检索到针对纯抓取行为的处罚案例，不排除存在未公开案例。

### 16.5 域外效力：两部法都按"行为指向谁"而非"主体在哪"

| | GDPR Art. 3(2) | 个保法第 3 条第 2 款 |
|---|---|---|
| 触发 | (a) 向欧盟数据主体提供商品/服务；(b) **监控**其行为 | (a) 以向境内自然人提供产品/服务为目的；(b) **分析、评估**境内自然人行为 |
| 判断依据 | 按**处理活动**，非按实体整体 | 措辞几乎照抄 GDPR |
| 附加义务 | Art. 27 指定欧盟代表 | **第 53 条：须在境内设专门机构或指定代表** |
| 执行 | Clearview 四国罚约 1 亿欧元（无欧盟实体），**均未支付** | Art. 42 黑名单：限制向该实体提供境内个人信息 |

> **个保法第 3 条的一个技术性缺口（未验证）**：纯 B2B 工具、客户全在境外、不向中国用户提供服务时，
> 是否落入(b)项"分析评估"存在解释空间，无公开执法案例。
> **但不宜依赖**——一旦产品输出包含中国用户画像或行为分析，(b) 项直接命中。

### 16.6 境外主体抓中国平台：管辖成立，执行看路径

- **刑法第 6 条第 3 款**："犯罪的行为或者结果**有一项**发生在中华人民共和国领域内的，
  就认为是在领域内犯罪。"目标服务器在境内 = 结果地在境内，**属地管辖成立**。
- **但管辖权成立 ≠ 能执行**：境外主体、人员、资产的实际执行需引渡或司法协助，门槛极高。
- **民事路径才是真威胁**：中美判决相互承认已有可行路径
  （*Northeast Securities v. Que Wenbin*, Cal. 2025，2.95 亿元人民币中国判决在美获承认）。
- **最现实的威胁是非司法手段**：平台直接在你注册地起诉（LinkedIn/Meta/X 的常规做法），
  或走 DMCA、应用商店、支付通道、云服务商下架——**腾讯 2026-01 一次打掉 4,195 个仓库，不需要任何法院。**

### 16.7 境内主体抓境外平台：执法真空但法律有效

- 中国法仍适用（行为地在境内，属地管辖成立；数安法、个保法适用于境内处理活动）
- 叠加境外法：ToS 管辖通常在加州/爱尔兰；含欧盟用户则 GDPR 适用；破解技术措施则触 §1201
- **额外的中国特有风险**：访问境外平台涉及《计算机信息网络国际联网管理暂行规定》第 6 条；数据出入境合规
- **但被抓平台在中国境内无实体，几乎不可能来中国起诉**——这使该象限成为**执法真空但法律有效**的灰区

## 17. 四象限决策矩阵

| | **目标：中国平台**（抖音/小红书/视频号/微博）| **目标：国际平台**（YouTube/X/Reddit/IG）|
|---|---|---|
| **主体：境内** | **最高风险 / 不可行**<br>刑法 285 全套 + 反法 + 个保法 + 平台民事诉讼**全部可实际执行**。平台在境内有实体，取证与诉讼成本极低。**无合规路径。** | **中风险 / 灰区可行**<br>中国法属地管辖成立但无被害人报案，执法真空。境外法：ToS 违约 +（若破解）§1201 +（若含欧盟用户）GDPR。<br>**前提**：仅登出抓公开数据、不破解加密、遵守 robots.txt、输出不含 EU/CN 个人画像 |
| **主体：境外**（新加坡/香港/BVI）| **中高风险 / 有限可行**<br>刑事敞口大幅下降，但个保法第 3 条(b) 仍适用且第 53 条要求境内代表；Art. 42 黑名单；平台可在你注册地起诉并申请中国判决承认执行；DMCA/云厂商/应用商店下架不需法院。<br>**降低的是刑事敞口，不是合规性。** | **最低风险 / 可行**<br>美国：登出抓公开数据基本安全（hiQ + Meta v. Bright Data + X v. Bright Data 三案叠加）。新加坡 PDPA 有公开数据免同意例外。<br>**剩余硬约束**：GDPR、开源 license、§1201、ToS（若登录）|

**最可行象限：境外主体 × 国际平台 × 仅登出公开数据 × 不破解加密 × 输出不含 EU/CN 个人画像。**

但要清醒：**这已经不是"多平台全站采集"了，是一个受限得多的产品。**

### 17.1 对"用自有账号登录后采集"这一需求的跨辖区结论

需求方最初选定的采集边界是"用自有账号登录后采集"。跨辖区看，这个选择在**任何**辖区都是最差的一档：

- 中国：突破访问控制的认定基础，落入刑法 285 条 2 款射程
- 美国：**登录恰好是 hiQ / Meta v. Bright Data 保护范围的边界**——
  两案的胜诉理由都是"登出状态"，一旦登录，ToS 约束恢复，Ryanair v. Booking.com 的 CFAA 认定就有了适用空间
- 欧盟：登录后数据几乎必然含个人信息，GDPR 全套义务触发
- 新港：CMA s.3 的"正常不可达部分"认定更容易成立

**换句话说：登录态采集是唯一一个换辖区也不会变好的选择。**
