# 传统集群部署

ThreadBeacon 的集群形态把职责分成三层：已有私有控制面负责身份、任务、数据库和审计；Gateway
接收位于 NAT/防火墙后的 Agent 主动建立的 WebSocket；Agent 与同 Pod Chromium 执行采集
和受控浏览器动作。这样 Sites 控制面不需要开放入站 TCP，也不会把浏览器登录态上传到云端。

## 单机验证

准备互不相同的强随机密钥并启动：

```bash
export THREADBEACON_CONTROL_URL=https://your-private-control-plane.example
export THREADBEACON_NODE_REGISTRATION_KEY=replace-with-control-plane-registration-key
export THREADBEACON_GATEWAY_AGENT_TOKEN=replace-with-agent-transport-token
export THREADBEACON_GATEWAY_CONTROL_TOKEN=replace-with-control-dispatch-token
export THREADBEACON_GATEWAY_PUBLIC_URL=https://gateway.example.com
docker compose -f compose.cluster.yaml up --build -d
```

默认仅在宿主机回环地址发布 Gateway `8789`。若控制面位于外部，必须用带 TLS 的反向代理
把它发布为 `wss://`/`https://`，再将该地址登记到控制面；Agent token 和控制派发 token
不能复用。

## Kubernetes / Helm

先分别构建并推送 `infra/gateway/Dockerfile`、`infra/worker/Dockerfile` 和
`infra/browser/Dockerfile`。使用现有 Secret，避免把密钥写入 values 文件：

```bash
kubectl -n threadbeacon create secret generic threadbeacon-execution-secrets \
  --from-literal=gateway-agent-token='...' \
  --from-literal=gateway-control-token='...' \
  --from-literal=node-registration-key='...'

helm upgrade --install threadbeacon infra/helm/threadbeacon-execution \
  --namespace threadbeacon --create-namespace \
  --set controlPlane.url=https://your-private-control-plane.example \
  --set gateway.existingSecret=threadbeacon-execution-secrets \
  --set controlPlane.existingSecret=threadbeacon-execution-secrets \
  --set gateway.publicUrl=https://gateway.example.com \
  --set gateway.image.repository=registry.example/threadbeacon-gateway \
  --set agents.image.repository=registry.example/threadbeacon-worker \
  --set browser.image.repository=registry.example/threadbeacon-browser
```

Chart 使用 StatefulSet 为每个 Agent 保留独立 Worker 身份和 Chromium Profile，滚动更新
不会把登录态串到其他节点；Gateway 使用 Deployment，Agent 仅通过集群内 WebSocket 主动
连接。noVNC/CDP 默认没有公网入口，需要调试时使用 `kubectl port-forward` 或受身份保护的
内部跳板。

Chart 只在受 NetworkPolicy 约束的 Pod 网络里设置
`THREADBEACON_GATEWAY_ALLOW_INSECURE_WS=1`。跨节点、跨集群或公网 Agent 必须使用 Ingress TLS 和
`wss://`，不得把这个开关复制到公网部署。

CDP `9222` 只在 Worker 与 Chromium 共用的 Pod 内通过 loopback 访问，NetworkPolicy 不允许
其他 Agent Pod 横向连接。noVNC `6080` 也只允许带 `threadbeacon.dev/browser-operator=true` 标签的
运维 Pod 访问；日常调试优先使用临时 `kubectl port-forward`。

当前 Gateway 的会话目录在单进程内存中，因此 Chart 明确默认 `replicaCount: 1`；Worker /
Browser 可以横向扩容。只有在跨 Gateway 的 Agent 目录和派发路由接入共享协调存储之后，
才应把 Gateway 扩为多副本。本限制不会影响执行节点的分布式扩展，但避免虚假的控制层 HA。

Gateway 会使用注册密钥把自身登记为 `gateway-ws` 聚合节点，并通过认证心跳上报当前 Agent
能力、总并发和活动任务；控制面只保存加密后的 Gateway HTTPS 地址与派发 token。各 Agent
仍以空数据平台能力注册到控制面，用于心跳和浏览器动作队列，数据采集任务只走反向 WS，
不会同时被 polling 抢走。
