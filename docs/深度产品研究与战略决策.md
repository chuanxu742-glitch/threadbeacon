# ThreadBeacon 深度产品研究与战略决策

> 研究日期：2026-08-30  
> 研究对象：当前 `main` 分支、公开仓库、相邻产品与公开数据通道  
> 文档目的：决定 ThreadBeacon 先为谁解决什么问题，以及下一阶段哪些能力应该停止、补齐或验证

## 0. 结论先行

ThreadBeacon 不应继续以“通用 Agent 情报平台”或“多平台舆情工具”作为首个市场定位。

建议先收敛为：

> **面向技术产品、AI 与 SaaS 团队的开源自托管持续竞品研究工作台：把用户自备或授权的官网、更新日志、RSS、GitHub、Hacker News、YouTube 等来源，持续转化为经人工复核、带出处、可交付的竞品变化简报。**

这不是产品永久边界，而是当前最可验证的切入口。它避开了三场暂时打不赢的战争：

1. 不与 Meltwater、Brandwatch 比全网数据覆盖和授权数据资产。
2. 不与 n8n、Dify 比通用工作流节点数量。
3. 不与 Hunchly 比法证级网页保存，也不与 OpenCTI 比垂直知识图谱。

当前产品成熟度应定义为 **alpha / 设计伙伴验证阶段**。版本号是 `0.8.0`，但尚无证据证明目标用户能稳定完成“研究问题 -> 来源 -> 运行 -> 复核 -> 交付”的业务闭环。此时最重要的不是继续增加平台能力，而是用一个真实场景验证产品价值。

## 1. 研究方法与证据等级

本报告使用三类证据，避免把判断写成事实：

| 标记 | 含义 | 使用方式 |
|---|---|---|
| **仓库事实** | 可由当前代码、迁移、测试或公开仓库直接验证 | 可直接用于排期和风险判断 |
| **外部事实** | 来自竞品官网、官方文档、平台条款或公开仓库 | 用于判断市场基线和边界 |
| **待验证假设** | 对用户、购买理由、付费意愿或使用频率的推断 | 必须通过访谈和试点验证 |

截至研究日，公开仓库只有 17 次提交、0 个 issue、0 个 fork，尚没有可观察的外部采用与留存信号。因此本报告不会把“市场需要”当作已验证结论。

## 2. 产品真相审计

### 2.1 已经具备的真实资产

| 资产 | 当前事实 | 产品价值 |
|---|---|---|
| 自托管执行骨架 | Spring Boot 控制面、PostgreSQL、MinIO、Worker、Compose/Helm | 适合数据和模型配置不能进入第三方 SaaS 的组织 |
| 受治理来源 | RSS、REST、公开网页、部分官方 API、OpenCLI/浏览器适配 | 可接用户自备或授权来源，不必绑定单一数据供应商 |
| 可重复运行 | 调度、Webhook、重试、租约、检查点、事件 Trace | 支持持续研究，而不只是一次聊天 |
| 证据关联雏形 | 分析主题可关联标准化记录和原始 URL | 有机会形成“结论可追溯”的差异化 |
| 团队与治理 | 工作区、RBAC、OIDC、PAT、审计、加密交付 | 具备从个人脚本走向团队工具的基础 |
| 可扩展执行 | 多来源 DAG、Skill、MCP、Dify 导入、浏览器动作 | 能承载后续研究方法，但不应成为普通用户首屏 |

这些资产证明 ThreadBeacon 不是 PPT 项目；它已经有一套相当完整的研究执行基础设施。

### 2.2 当前承诺与真实行为的差距

| 严重度 | 发现 | 仓库证据 | 产品影响 |
|---|---|---|---|
| **P0** | 项目模板只是标签，不会创建对应来源、流程或分析方法 | `PlatformService.TEMPLATES` 与 `createProject()` | 用户选择“竞品研究”后，实际体验与空白项目基本一致 |
| **P0** | 所有普通分析都使用同一套“用户痛点”提示词 | `src/pipeline/analyze.ts` 的 `SYSTEM_PROMPT` | 舆情、竞品、内容趋势三个模板无法兑现各自承诺 |
| **P0** | 报告没有稳定的 `project_id` / `workflow_run_id` 归属 | `reports` 表及 `JobService.completeTransaction()` | 项目不能成为成果容器，团队无法按研究问题回看历史 |
| **P0** | `evidence.project_id` 存在但写入时未赋值 | `JobService.persistEvidence()` | 证据页显示的是工作区全局集合，不是真正的项目证据库 |
| **P0** | 记录去重时覆盖正文、指标和 `raw_json`，没有版本表 | `JobService.persistRecord()` | 无法证明某次结论使用的是哪个历史版本，也无法可靠做变化检测 |
| **P0** | “可靠性”只由参与聚类的文本数量决定 | `gradeQuality()` 中 50/200 两档阈值 | 没有考虑来源多样性、时间范围、缺失来源、重复与引用有效性，`reliable` 容易过度承诺 |
| **P0** | 报告详情仍以最多 6 个卡片加原始 JSON 为主 | `apps/control-plane/web/main.tsx` 的 `ReportPage` | 还不是团队可以直接阅读、复核和转发的决策产物 |
| **P1** | 关系图的 `co-supports` 来自同簇共现，固定置信度 80 | `JobService.persistEvidence()` | 这是聚类投影，不是经过验证的实体或因果关系 |
| **P1** | DAG 中 cluster/llm/report 节点主要确认固定分析管线已经做过，部分后处理不改变主报告 | `src/worker.ts` 的 `executeWorkflowPostProcessing()` | 画布的自由度高于实际研究语义，容易形成“流程已执行”的错觉 |
| **P1** | 团队只有权限协作，没有发现级评论、复核、批准或驳回 | 当前 schema 与 UI | RBAC 已有，但团队研究工作本身还没有协作闭环 |
| **P1** | 只有运行指标，没有产品激活和成果采用指标 | Actuator/Micrometer 指标与前端代码 | 无法知道用户是否获得价值，只能知道系统是否工作 |
| **P1** | 首次部署需要数据库、对象存储、Java、Node、Worker、模型与来源配置 | README 启动路径 | 自托管是优势，同时也是激活漏斗中最大的摩擦 |

### 2.3 必须停止使用的过度表述

在对应能力补齐前，不应对外使用以下承诺：

- “全网舆情”或“全平台采集”：平台授权、成本、地区和登录态边界不允许这样承诺。
- “法证级证据”或“法院可采”：当前没有不可变版本、内容哈希、签名、可信时间戳和完整保全链。
- “可信 AI 结论”：当前更准确的说法是“可回到来源记录的 AI 聚类摘要”。
- “可视化编排任意研究方法”：当前执行管线仍以固定的采集、聚类和痛点归纳为主。
- “企业级产品”：具备部分企业基础设施，不等于完成了企业用户工作流和生产验证。

## 3. 竞争格局

### 3.1 五类替代方案

| 类别 | 代表产品 | 用户购买的核心理由 | ThreadBeacon 不应硬拼的部分 | 可利用的空白 |
|---|---|---|---|---|
| 企业市场/媒体情报 | AlphaSense、Feedly、Meltwater、Brandwatch | 授权数据覆盖、搜索、监测、仪表盘、团队报告 | 数据库规模、媒体版权、全网覆盖、成熟销售服务 | 自托管、用户自备来源、可编排方法、开放数据出口 |
| AI 研究助手 | NotebookLM、Perplexity Enterprise | 上手快，基于来源直接问答并给引用 | 单次研究体验、模型能力、内部知识连接器 | 持续运行、来源健康、版本化研究方法、交付与审计 |
| 采集与自动化平台 | Apify、n8n、Dify | 连接器多、画布灵活、能嵌入业务系统 | 节点生态、通用自动化、云端执行规模 | 研究问题、发现、证据、复核、报告等领域对象 |
| 开源趋势监测 | TrendRadar、changedetection.io | 部署快、热点/RSS/网页变化、低成本推送 | 极简激活、中文热点覆盖、社区势能 | 从“有变化”推进到“变化意味着什么、依据是什么、谁复核了” |
| 调查与证据工作台 | Hunchly、OpenCTI、OSINTracker、Scope Intelligence | 案件组织、关系、证据保存、可追溯报告 | Hunchly 的保全能力、OpenCTI 的垂直模型、Scope 的版本化证据语义 | 面向非安全研究团队的持续监测、研究模板、团队审批和自动交付 |

### 3.2 最需要重视的直接竞品

#### TrendRadar

[TrendRadar](https://trendradar.sandev.cc/en/) 已经把“多平台热点 + RSS + AI 分析 + 多渠道推送 + MCP + Docker”做成极低门槛产品。其公开仓库有大量社区活动，说明“轻量趋势监测”已是拥挤赛道。

ThreadBeacon 不能靠更多平台名称获胜。差异必须落到项目制研究、来源治理、变化基线、发现复核和证据报告。

#### Scope Intelligence

[Scope Intelligence](https://github.com/Samarth-23-eng/scope-intelligence) 与 ThreadBeacon 的表述高度重合：自托管、公开来源、AI 研究、关系、监测、证据与报告。Scope 已公开强调不可变文档版本、引用完整性、矛盾、人工复核和变化时间线。

这意味着“evidence-first self-hosted OSINT”本身不是足够独特的定位。ThreadBeacon 必须在 **团队研究运营 + 可复用研究方法 + 受治理执行** 上形成具体体验，而不是继续停留在同一组名词。

#### Hunchly

[Hunchly](https://hunch.ly/) 的核心是自动捕获页面、URL、时间戳和哈希，并形成透明审计链与调查报告。它教育了市场：真正的证据产品首先要保证保存和完整性，然后才谈 AI。

ThreadBeacon 当前更适合说“出处可追溯”，不应说“法证证据”。

### 3.3 数据边界决定了不能先做消费社媒舆情

- [Reddit Data API 条款](https://redditinc.com/policies/data-api-terms) 要求商业用途另行签约。
- [TikTok Research API](https://developers.tiktok.com/products/research-api/) 只向符合条件的研究人员开放，并有地区与用途限制。
- [YouTube Data API](https://developers.google.com/youtube/v3/determine_quota_cost) 有独立搜索配额和每日配额约束。
- [Bluesky 协议服务](https://bsky.network/docs/protocol-services/) 提供开放实时数据，但实时流不等于历史检索覆盖。

因此首个可交付场景应该优先依赖官网、RSS、公开网页、GitHub、HN、YouTube 等来源，并允许客户自行补充已获授权的连接。ThreadBeacon 卖的是研究流程软件，不是数据许可。

## 4. 推荐 ICP 与待办任务

以下属于 **待验证假设**，不是已经确认的客户画像。

### 4.1 推荐首个 ICP

| 维度 | 假设 |
|---|---|
| 组织 | 50-2000 人的 AI、开发者工具、SaaS 或技术服务公司 |
| 使用团队 | 2-10 人的产品营销、竞争情报、产品战略、创始人办公室或研究团队 |
| 购买者 | 产品营销负责人、战略研究负责人、产品运营负责人 |
| 部署影响者 | 数据/平台工程师、安全或 IT 管理员 |
| 高频任务 | 每周跟踪 5-30 个竞品的产品、定价、定位、生态和市场信号变化 |
| 当前替代方案 | RSS/Feedly + 浏览器收藏 + 表格/Notion + 通用 LLM + 人工周报 |
| 触发条件 | 来源分散、重复劳动高、报告结论难追溯、内部资料不能交给外部 SaaS |
| 排除条件 | 只需要一次性搜索；必须购买全网社媒数据；要求法院级证据；没有人负责复核 |

### 4.2 核心 JTBD

> 当我需要持续掌握竞品变化并向产品或管理层汇报时，我希望系统自动检查我信任的来源，告诉我“发生了什么、为什么值得关注、证据在哪里、还有什么不确定”，让我能快速复核并交付，而不是每周重新打开几十个页面和拼接一份没有出处的摘要。

功能性任务：

- 维护要跟踪的公司、产品、主题和可信来源。
- 发现相对上次运行真正发生的变化，而不是重新总结所有内容。
- 把变化归入产品、定价、定位、生态、招聘、客户反馈等研究框架。
- 对每条发现查看来源版本、原文片段、时间和分析方法。
- 批准、编辑、驳回发现，并记录未知项或反证。
- 形成周报并交付到团队已有渠道。

情绪与社会任务：

- 面对管理层追问时能迅速回答“这个判断从哪里来”。
- 减少因遗漏关键变化而产生的不安。
- 让研究员的价值体现在判断与复核，而不是搬运链接。

## 5. 为什么选择“持续竞品研究”作为切口

| 备选定位 | 来源可行性 | 当前能力复用 | 差异化空间 | 首次价值速度 | 判断 |
|---|---:|---:|---:|---:|---|
| 全网舆情/社交聆听 | 低 | 中 | 低 | 中 | 放弃，授权数据是硬门槛 |
| 通用 AI 工作流 | 高 | 高 | 低 | 低 | 放弃，n8n/Dify 生态远强 |
| 法证 OSINT 调查 | 中 | 中 | 中 | 低 | 暂缓，证据保全要求未满足 |
| 企业市场情报搜索 | 中 | 中 | 低 | 中 | 暂缓，缺少授权内容库 |
| 持续竞品研究 | 高 | 高 | 中高 | 高 | **推荐首个切口** |

推荐切口还有一个现实好处：可以先用 3-5 类可治理来源做出完整体验，不需要等待所有社交平台接入。

## 6. 产品对象应如何重构

当前系统以 Job、Worker、Node 为强对象；目标产品应以研究项目和发现为强对象。

```text
Workspace
  -> Project（研究问题、决策背景、跟踪对象、节奏、负责人）
      -> Source（来源、授权/法律基础、健康、版本、范围）
      -> Playbook（研究方法模板，默认隐藏底层 DAG）
          -> Run（一次按不可变版本执行的研究）
              -> Observation（某个来源在某时刻的不可变观测）
              -> Finding（系统提出的可复核发现）
                  -> Evidence Link（精确引用 Observation/片段）
                  -> Review（批准、编辑、驳回、评论、反证）
              -> Report（被批准发现的版本化交付物）
                  -> Delivery（送达状态与阅读/采用信号）
```

对象定义：

| 对象 | 必须回答的问题 |
|---|---|
| Project | 我们在研究什么，准备支持哪个决策，谁负责，多久更新一次？ |
| Source | 为什么信任/允许使用它，当前是否可用，上次成功和变化是什么？ |
| Playbook | 用什么方法从观测生成发现，模板版本是什么？ |
| Observation | 在什么时间从哪里看到了什么，内容是否被修改？ |
| Finding | 发生了什么，重要性是什么，置信度和未知项是什么？ |
| Evidence Link | 该发现由哪条不可变观测的哪个片段支持或反驳？ |
| Review | 谁做了什么判断，是否编辑或拒绝，理由是什么？ |
| Report | 哪些已复核发现面向哪个受众，以什么版本交付？ |

## 7. 首个黄金路径

### 7.1 用户可见路径

1. 创建“竞品变化追踪”项目，填写研究问题和报告接收者。
2. 添加 3-10 个竞品或产品，并选择官网、更新日志、RSS、GitHub、HN、YouTube 等来源。
3. 系统逐一测试来源，清楚显示“可运行、需要配置、受限、不可用”，不展示 Worker 术语。
4. 首次运行建立基线，只生成“当前画像”，不把所有历史内容误报为新变化。
5. 后续运行只突出新增、修改、消失和跨来源印证的信号。
6. 报告草稿按“变化 -> 影响 -> 证据 -> 置信度 -> 待验证项”展示。
7. 研究员批准、编辑或驳回每条发现；报告只纳入已批准内容。
8. 周报交付到飞书、邮件或 Webhook，并保留版本和复核记录。

### 7.2 默认研究方法

“竞品研究”模板必须改变执行行为，而不只是换标题：

```text
建立来源基线
  -> 采集增量和内容版本
  -> 识别真实变化
  -> 分类：产品 / 定价 / 定位 / 生态 / 招聘 / 市场信号
  -> 生成发现：变化、影响、引用、置信度、未知项
  -> 跨来源印证或标记“单一来源”
  -> 人工复核
  -> 生成版本化周报
```

底层 DAG 可以继续存在，但默认用户只选择模板、对象、来源、频率和质量门槛。高级模式再暴露画布。

## 8. P0 产品薄片

在首个设计伙伴验证前，只做以下能力：

### 8.1 必须补齐

| 顺序 | 能力 | 验收标准 |
|---:|---|---|
| 1 | 项目身份贯穿 | Job、Run、Observation、Finding、Report、Delivery 都能追溯到同一项目 |
| 2 | 不可变观测版本 | 同一来源内容变化时新增版本；保存内容哈希、采集时间、原始 URL 和对象存储引用 |
| 3 | 真正的竞品模板 | 模板创建默认研究框架，并让分析输出“变化/影响/证据/未知项” |
| 4 | 发现复核 | 支持批准、编辑、驳回；报告默认只使用已批准发现 |
| 5 | 可读报告 | 摘要、变化分类、发现、精确引用、来源覆盖、方法/版本、未知项，不以 JSON 为主要界面 |
| 6 | 来源就绪 | 每个来源显示能力、授权边界、配置缺口、最近成功、连续失败和受影响项目 |
| 7 | 激活埋点 | 能计算首次项目、首个就绪来源、首轮运行、首条复核发现、首次交付的转化与耗时 |

### 8.2 暂停扩张

在完成 3 个真实设计伙伴试点前，暂停：

- 新增更多社交平台名称。
- 扩展通用 DAG 节点。
- 扩展 Skill 蒸馏和自动纠错能力。
- 扩展更多集群部署选项。
- 做通用聊天助手或大而全的首页仪表盘。
- 把插件数量当成产品进度。

这些能力不是没价值，而是目前不会证明用户愿意持续使用 ThreadBeacon。

## 9. 六周执行建议

| 周次 | 产品工作 | 工程工作 | 研究/验证 |
|---|---|---|---|
| 第 1 周 | 锁定竞品研究脚本与报告样例 | 设计项目贯穿与 Observation/Finding schema | 访谈 6 位目标用户，收集最近一次真实周报 |
| 第 2 周 | 做可点击报告与复核原型 | 数据迁移、项目归属、记录版本 | 再访谈 6 位，测试概念和字段语言 |
| 第 3 周 | 打通项目创建、来源就绪、首次基线 | 实现 baseline/delta 与模板执行配置 | 招募 3 个设计伙伴，导入真实来源 |
| 第 4 周 | 打通发现复核与报告 | 精确证据引用、报告 API、审计 | 每个伙伴完成第一次共同研究 |
| 第 5 周 | 打通定时运行和交付 | 交付版本与采用事件 | 观察无人陪伴的第二次运行 |
| 第 6 周 | 只修试点阻塞问题 | 质量、恢复、导出与性能补强 | 做续用复盘，决定继续、调整或停止该切口 |

## 10. 用户研究计划

### 10.1 访谈样本

两周内完成 12 次 45 分钟访谈：

- 5 位产品营销或竞争情报从业者。
- 3 位产品战略、产品运营或创始人办公室成员。
- 2 位咨询/研究机构分析师。
- 2 位负责部署研究工具的平台或安全人员。

前 25 分钟不演示产品，只追问最近一次真实任务：

- 上一次竞品周报是什么时候做的？谁提出，谁阅读，支持了什么决策？
- 从收到问题到交付经历了哪些步骤？请展示允许分享的模板或空白结构。
- 哪一步最耗时，哪一步最容易被质疑？
- 哪些来源必须看？漏掉哪个会造成严重后果？
- 目前如何保存证据、处理删除/修改、验证 AI 输出？
- 现有工具花多少钱、多少人时，为什么没有被替换？
- 哪些数据绝不能进入第三方 SaaS？谁有采购和部署否决权？

后 20 分钟用报告原型测试：

- 让受访者指出第一眼会点哪里、会质疑哪条信息。
- 要求其删除三个“看起来有用但不会影响工作”的功能。
- 询问愿意用哪一组真实来源参加两周试点，不询问抽象的“是否愿意使用”。

### 10.2 问题成立门槛

满足以下条件才进入工程 P0：

- 至少 8/12 人每月至少执行一次同类任务。
- 至少 6/12 人每周为该任务投入 4 小时以上。
- 至少 6/12 人遇到过出处追问、遗漏来源或重复搬运问题。
- 至少 4/12 人有明确的自托管、BYOK 或数据驻留要求。
- 至少 3 家愿意拿真实来源和真实交付物参加两周试点。

没有达到门槛时，不用更多功能“教育市场”，应调整 ICP 或场景。

### 10.3 设计伙伴试点成功门槛

| 指标 | 门槛 |
|---|---:|
| 管理员从开始部署到系统就绪 | <= 30 分钟 |
| 研究员从创建项目到首份基线报告 | <= 20 分钟，不含采集等待 |
| 自动发现的引用可打开且支持对应结论 | >= 95% |
| AI 发现被批准或编辑后批准的比例 | >= 60% |
| 相比原流程节省的研究员时间 | >= 40% |
| 第二周仍主动运行并交付报告的伙伴 | >= 2/3 |
| 试点结束后愿意继续使用或付费支持 | >= 2/3 |

## 11. 指标体系

### 11.1 北极星指标

> **每周被复核并交付的有效发现数（Weekly Verified Findings Delivered）**

一条有效发现必须同时满足：

- 属于一个活跃研究项目。
- 至少关联一条可打开的不可变 Observation；单一来源要显式标记。
- 经研究员批准，或编辑后批准。
- 进入一个已交付报告。

这个指标同时约束采集、分析、证据、复核和交付，不能靠增加任务量刷高。

### 11.2 激活漏斗

```text
workspace_ready
  -> project_created
  -> source_ready
  -> baseline_completed
  -> finding_reviewed
  -> report_delivered
  -> second_report_delivered
```

重点看每一步转化率、中位耗时和失败原因。系统运行指标仍保留，但与产品指标分开。

### 11.3 质量与护栏指标

| 指标 | 目的 |
|---|---|
| 引用有效率 | 发现能否回到对应版本和片段 |
| 来源覆盖率 | 计划来源中成功采集的比例 |
| 单一来源发现占比 | 防止把未经印证的信号包装成确定事实 |
| 驳回率与编辑率 | 观察 AI 输出是否真正可用 |
| 变化误报率 | 防止模板、导航、时间等噪声进入周报 |
| 未知项关闭率 | 研究是否形成后续验证循环 |
| 来源受限/失败占比 | 识别不应继续承诺的平台 |
| 每份报告人工耗时 | 判断是否真的节省研究时间 |

## 12. 包装与商业模式假设

当前先验证使用，不急于做收费墙。Apache-2.0 可以继续作为采用入口。

建议的长期包装假设：

| 层级 | 提供内容 | 目的 |
|---|---|---|
| Community | 单机/自托管、BYOK、基础来源、一个研究模板、报告与导出 | 获得采用、反馈和贡献 |
| Team/Enterprise | 托管升级、SSO/SCIM、细粒度复核、保留策略、审计包、备份、支持 SLA | 为治理与运维价值收费 |
| Services | 来源适配评估、部署、研究模板定制、合规边界梳理 | 服务早期复杂客户并学习 |

不要销售“全网数据包”，除非未来获得明确、可转售的数据许可。产品收入应来自软件、治理、托管和支持。

## 13. 主要风险与停止规则

| 风险 | 早期信号 | 应对/停止规则 |
|---|---|---|
| 用户只要一次性 AI 搜索 | 没人愿意设置定时来源 | 退回研究助手或停止持续监测切口 |
| 自托管不是购买理由 | 目标用户都接受 NotebookLM/Feedly | 不再用复杂部署换取不存在的价值 |
| 来源覆盖不够 | 试点的关键来源多数不可合法/稳定接入 | 收窄行业或转为客户自有来源编排层 |
| AI 发现不可用 | 批准率低于 30%，编辑时间不低于人工写作 | 先做变化提取和证据整理，弱化自动结论 |
| 报告没人使用 | 交付成功但业务方不打开、不追问、不采取行动 | 重新定义受众和交付物，不优化采集吞吐 |
| 与 Scope/TrendRadar 无差异 | 用户把产品理解为更复杂的同类工具 | 强化团队复核与研究方法；仍无差异则停止 |

## 14. 对外表达

### 一句话

> ThreadBeacon 是面向技术产品与 AI/SaaS 团队的开源自托管持续竞品研究工作台，把用户授权的公开来源转化为可复核、可交付的变化简报。

### 三个价值点

- **持续，不靠重新搜索**：按项目维护来源基线，只突出真正变化。
- **有出处，不交黑盒摘要**：每条发现回到当时的来源版本和原文片段。
- **可复核，不让 AI 直接定稿**：研究员批准、编辑或驳回后再形成报告。

### 明确不是什么

- 不是承诺全网覆盖的社交聆听数据商。
- 不是面向所有自动化场景的通用工作流平台。
- 不是未经人工复核即可作为事实使用的 AI 搜索引擎。
- 当前不是法证取证工具。

## 15. 最终产品决策

1. 将产品阶段标记为 alpha / 设计伙伴验证，不再用基础设施完成度代替产品成熟度。
2. 首个 ICP 暂定为技术产品、AI 与 SaaS 团队中的竞品/战略研究角色。
3. 首个场景只做持续竞品变化简报。
4. 项目必须成为 Job、Run、Observation、Finding、Report 和 Delivery 的共同边界。
5. 把 `painPoints` 升级为按研究方法生成、可复核的 Finding；痛点只是其中一种类型。
6. 在说“可信/可审计”前，先实现不可变观测版本、精确引用和人工复核。
7. 普通用户默认使用 Playbook，不直接面对 DAG、Worker、Skill 九要素和 MCP。
8. 暂停新增平台和通用能力，直到 3 个设计伙伴完成两周真实试点。
9. 北极星指标改为“每周被复核并交付的有效发现数”。
10. 若访谈和试点未达到门槛，应调整定位，而不是继续扩建平台。
