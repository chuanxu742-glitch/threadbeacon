# ThreadBeacon 产品经理视角打磨路线图

> 本文保留为界面与近期打磨清单。产品战略、首个 ICP、竞争判断、停止规则和验证门槛以
> [`深度产品研究与战略决策.md`](./深度产品研究与战略决策.md) 为准；在设计伙伴验证前，
> “可信研究”是目标状态，不代表当前已经完成不可变观测、精确引用和发现复核。

## 0. 产品判断

ThreadBeacon 不应该再被包装成“采集工具”或“技术控制台”。它的主心智应该是：

> 研究团队围绕一个研究问题，持续接入可信来源，运行可复用研究流程，产出带证据链的报告，并交付给业务方。

因此产品打磨的重点不是继续堆平台入口，而是缩短第一份可信报告的路径、降低技术概念暴露、把运行风险变成可行动的待处理事项。

## 1. 目标用户与购买理由

| 用户 | 主要任务 | 购买理由 |
|---|---|---|
| 研究员 | 配来源、跑流程、看证据、写报告 | 少做重复采集和整理，结论能回溯 |
| 研究负责人 | 管项目、模板、节奏和交付 | 一次研究能沉淀为团队方法 |
| 系统管理员 | 管 Worker、授权、OIDC、审计和存储 | 自托管、凭据边界清楚、可审计 |
| 自动化负责人 | 把复杂流程做成 Skill / DAG | 让团队方法自动化，但保留确认和回滚 |

## 2. 当前产品状态

已具备的平台底座：

- 控制面：Java Spring Boot，已有身份、任务、工作流、记录、报告、Skill、集成、审计。
- 执行层：TypeScript Worker，支持能力上报、抢单、回传和浏览器自动化。
- 前端：已经收敛为“今天、项目、报告、自动化、团队与系统”的信息架构。
- 数据闭环：记录、证据、报告、Trace、JSON/CSV 导出均已存在。

主要缺口：

- 用户首次使用仍可能从“技术资源”开始，而不是从“研究问题”开始。
- 报告页还偏通用 JSON 渲染，缺少证据报告的产品化结构。
- 来源能力有目录，但缺少清晰的 readiness 分级和修复动作。
- 团队与系统入口已经出现，但成员邀请、角色、工作区切换需要成为稳定闭环。
- DAG/Skill/MCP/Dify/Browser Profile 的概念仍容易一起暴露，需要更严格的角色化入口。

## 3. 北极星指标

> 从新工作区到第一份可信研究报告的成功率。

配套指标：

| 指标 | 看什么 |
|---|---|
| 首个项目创建率 | 用户是否理解主对象是项目 |
| 首个来源试运行成功率 | 来源接入是否可行动 |
| 首份报告生成率 | 产品闭环是否跑通 |
| 报告打开率 | 报告是否成为成果中心 |
| 证据点击率 | 结论是否被复核 |
| 二次运行率 | 一次研究是否沉淀为持续流程 |
| 定时计划创建率 | 是否进入长期监测 |
| 待处理关闭时长 | 风险、失败、授权缺口是否可处理 |

## 4. P0：把第一份报告跑顺

### 4.1 今天页改成 Team Inbox + System Pulse

目标：用户一进来知道现在能不能跑研究，以及有什么阻塞。

必须聚合：

- 无执行节点 / 节点离线
- 失败任务 / 长时间排队
- 来源测试失败
- Skill 待确认动作
- 交付失败
- Browser Profile 失效
- Dify 导入阻断节点
- 最近生成但未打开的报告

验收：

- 无 Worker 时，主 CTA 是“配置执行节点”，不是“新建采集任务”。
- 有报告时，CTA 指向报告详情，不直接下载 JSON。
- 待处理项都能跳到解决位置。

### 4.2 项目创建从“空白配置”变成“研究问题”

目标：先让用户说清楚研究目标，再自动落到来源和流程。

建议模板：

- 市场舆情监测
- 竞品动态追踪
- 内容趋势雷达
- 官网 GEO 观测
- 空白项目

创建表单最小字段：

- 研究问题
- 目标对象或关键词
- 来源类型
- 运行频率
- 报告接收方

验收：

- 创建后自动生成默认来源建议、线性研究流程和报告结构。
- 来源未就绪时显示 blocked reason 和修复动作。

### 4.3 报告详情页产品化

目标：报告是团队成果，不是对象存储里的 JSON。

报告页最小结构：

- 摘要
- 关键发现
- 痛点 / 主题
- Top 证据
- 原文链接
- 数据量、来源、时间范围
- 运行版本和 Trace
- 导出、复制摘要、配置交付

验收：

- Dashboard 和项目页进入同一个报告详情页。
- 报告中每个发现都能看到关联记录。
- 原始 JSON 放在高级折叠区。

### 4.4 来源能力变成 Readiness，而不是平台列表

状态分级：

| 状态 | 含义 |
|---|---|
| ready | 当前项目可运行 |
| missing_resource | 缺 Worker、key、Profile 或来源配置 |
| needs_authorization | 需要账号授权或 API key |
| policy_blocked | 策略或合规阻断 |
| unverified | 代码存在但未真实验收 |
| degraded | 可运行，但交付、配额或历史覆盖受限 |

验收：

- 用户不会误以为“目录里有平台”就是“当前可运行”。
- 每个 blocked reason 都有下一步动作。

## 5. P1：让团队稳定协作

### 5.1 团队与系统入口收敛

放入：

- 工作区切换
- 成员与角色
- 执行节点
- 来源账号授权
- 开发者接口 / MCP
- Dify 导入
- Webhook / Delivery
- 审计日志

不要放入：

- 普通研究员日常项目页不需要的 token、CDP URL、runtime_json、raw capability。

### 5.2 普通流程与高级 DAG 分层

普通模式：

```text
来源 → 清洗 → 聚类 → AI 总结 → 证据报告 → 交付
```

高级模式：

- 自由 DAG
- Gate / Agent / Dataset / Deliver 节点
- 上游依赖配置
- Skill 绑定
- Dify 导入节点

验收：

- 研究员不拖 DAG 也能跑第一次研究。
- 自动化负责人仍能打开完整 DAG。

### 5.3 Skill 从九要素表单变成团队自动化助手

默认展示：

- 可用助手
- 模板
- 最近运行
- 待确认动作
- 纠错提案

高级入口再展示：

- SKILL.md
- 九要素
- 不可变版本
- 回滚

## 6. P2：产品化交付与可信边界

### 6.1 Delivery 分清提交成功和业务成功

产品状态：

- 已提交
- 已送达
- 被拒收
- 等待确认
- 未知结果
- 重试中
- 失败

验收：

- HTTP 200 不直接等于“业务已完成”。
- 未知结果进入待处理。
- 重试复用同一个 operation id。

### 6.2 合规边界进入产品语言

对外只承诺：

- 开放协议
- 官方 API
- 公开网页且遵守 robots
- 用户授权的自有账号数据
- 已签约供应商数据

不承诺：

- 封闭平台全网监听
- 登录态全站采集
- 签名逆向
- 绕过访问控制

## 7. 近期建议排期

| 周期 | 目标 | 交付物 |
|---|---|---|
| 第 1 周 | 对齐定位与首屏闭环 | 文案统一、今天页待处理、报告入口统一 |
| 第 2 周 | 项目创建和来源 readiness | 项目模板、来源状态、blocked reason |
| 第 3 周 | 报告详情产品化 | 摘要、发现、证据、Trace、导出 |
| 第 4 周 | 团队与系统闭环 | 成员、工作区、执行节点、授权、审计入口 |
| 第 5 周 | 自动化能力分层 | Skill 模板、待确认、纠错、DAG 高级入口 |
| 第 6 周 | 交付和验收 | Delivery 状态、真实凭据 smoke、产品验收清单 |

## 8. 关键产品决策

1. 主对象是研究项目，不是任务。
2. 核心成果是证据报告，不是 JSON。
3. Worker、MCP、Dify、Browser Profile 是内置能力，不是研究员主导航。
4. 平台能力必须按当前工作区和项目判断 readiness。
5. 安全阻断不是失败，要产品化为可解释状态。
6. 报告必须能回到证据、记录、运行版本和 Trace。
7. 团队协作是 P0，不是企业版彩蛋。
8. 不用“全平台采集”做卖点，用“可信研究闭环”做卖点。
